## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Represent the interactive Pi client as a durable server-authoritative AgentActor execution profile. User input, actor delivery, self-continuation, settlement, and completion live in its mailbox while the local Pi process remains a fenced model/tool executor. Reincarnations catch up unfinished work, and isolated introspection automatically resumes future-action promises instead of requiring another user turn.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 Interactive user input is durably admitted to the Client AgentActor mailbox before model execution and is deduplicated by server-issued turn identity
- [ ] #2 Exactly one fenced client incarnation may execute and settle model-bearing work while other connections remain observers
- [ ] #3 Every settled interactive turn runs isolated introspection and a future-action promise without terminal evidence durably enqueues a bounded self-continuation
- [ ] #4 Client reincarnation adopts mailbox and settlement high-water, replays unfinished turns exactly once, and resumes the active thread without polling
- [ ] #5 Tell, Ask, user turn, self-continuation, waiting, blocked, completion, and presentation ACK retain distinct typed semantics
- [ ] #6 Raw reasoning and credentials never enter durable state; only bounded owner-private input, result, checkpoint, tool receipts, and protocol identity are retained
- [ ] #7 Race-safe protocol, daemon, actor-client, restart, duplicate, fencing, introspection, and live E2E tests prove user → client mailbox → local Pi → introspection → automatic continuation → terminal response
<!-- AC:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
Frozen TASK-26 contract before implementation:
1. Authority model: Client AgentActor is the only authority for turn admission, routing, execution state, settlement, introspection decisions, continuation enqueue, replay, and presentation obligations. Local Pi is a fenced, untrusted model/tool executor and projection UI only.
2. Protocol families: keep Tell, Ask, UserTurn, SelfContinuation, Waiting, Blocked, Completion, PresentationAck, Introspection, ExecutorLifecycle, and replay/snapshot messages typed and non-interchangeable. Cross-actor work remains explicit ActorMessage Ask/Tell with normal source outbox and hop/chain limits.
3. Durable ordering: use one monotonic per-actor durable log order for admission, lease claim/renew/expire/revoke, delivery, settlement, introspection, continuation, completion, and presentation event creation. Snapshots are rebuild aids; reconnect resumes from snapshot plus log replay after snapshot seq.
4. Admission: UserTurn admission is durable, idempotent by proposed turn id/content digest/schema version, and required before execution. Admission decisions define token expiry/single-use/invalidation on epoch changes. Deferred/rejected decisions preserve local draft and do not execute.
5. Fencing/leases: exactly one active executor lease/generation may execute model-bearing work. All mutating executor/client requests and executor-originated events include actor id, actor epoch, executor generation, lease/fence, turn/work id, delivery seq, message id, causation/correlation IDs, idempotency key, timestamp, and schema version. Stale/future/mismatched tuples fail before payload parsing.
6. Turn state machine: define machine-checkable states and transitions for admitted, claimed, running, waiting, blocked, settled, introspecting, continuation_queued, completed, failed, and presented. Waiting/Blocked carry durable wake predicates, retry/deadline policy, and replay behavior.
7. Settlement/idempotency: settlement is committed idempotently before side effects. Exact duplicate settlement returns the retained commit; conflicting duplicate degrades/fails closed. Introspection, continuation enqueue, completion, and presentation event creation are idempotent side effects keyed from durable source seqs.
8. Introspection/continuation: isolated introspection is advisory and server-authorized only after settlement, with strict bounded JSON, no tools/extensions/skills/session/actor bridge, no raw reasoning, duplicate-key rejection, and policy scan. The actor converts advisory terminal-evidence/future-action classification into typed state transitions. SelfContinuation is a new admitted mailbox item with deterministic identity, same-thread binding, budget/depth/deadline/backoff/byte caps, and no cross-actor targets.
9. Presentation: PresentationAck and delivery ACK are projection-only. They never advance mailbox execution, settlement, completion, or cross-actor delivery. Presentation is at-least-once replay with idempotent UI ACK; the practical TUI oracle is committed to render tree and not hidden by current viewport.
10. Privacy/security: raw reasoning and credentials are structurally impossible to persist. Durable state stores only bounded owner-private user input/final result text, redacted checkpoints, digests, receipts, and protocol identity. Observer projections and diagnostics are payload-free/redacted and exclude prompts, results, checkpoints, credentials, fences, handles, runtime/session/process/tmux details, paths, hostnames, and ports. Replay is authorized per incarnation.
11. Reconnect/reincarnation: clients resume with actor epoch/log cursor/snapshot id. Actor returns authorized snapshot plus log delta and reincarnation notice. Client replaces projection from actor state, clears stale admissions/commands/ACK obligations/affordances, preserves drafts, disables controls without current valid generation, and never replays old turns or lifecycle commands automatically.
12. Version/cutover: add protocol/state schema versions and explicit upgrade behavior. Legacy clients that lack admission, lease/generation, replay cursor, and PresentationAck support are rejected or downgraded to observers.
13. Test gates: implement daemon/protocol/actor-client/TUI/live E2E tests for durable-before-effects ordering, stale/future/mismatched fences, duplicate/tombstone ledgers, replay gaps/truncation/reordering/schema mismatch, crash windows after every durable step, old/new executor settlement races, privacy canaries across stores/logs/replay/errors/metrics/artifacts, bounded continuation loop exhaustion, and full UserTurn → executor → introspection → crash/reincarnation → replay → continuation decision → Completion → PresentationAck flow.
14. Implementation slices: first specify/generated protocol and state-machine tests; then daemon durable log/lease/admission/settlement; then actor-client frontend/TUI projection and ACK/replay; then isolated introspection/continuation; finally compatibility, chaos/restart, privacy, and live E2E gates with independent architecture/security/QA review before finalization.
